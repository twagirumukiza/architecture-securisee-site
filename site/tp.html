Partie 2 — Travaux pratiques

Réseau sécurisé pas à pas : DMZ, VLAN, pare-feu. Tutoriel sur Proxmox VE, pfSense et Kali Linux — environ 20 h. Chaque étape indique sur quelle machine travailler, quoi taper et ce que vous devez voir.

Avant de commencer

Ce cahier prolonge le cours « Architecture sécurisée ». Vous allez construire, configurer, attaquer puis durcir une architecture complète : double pare-feu, DMZ, VLAN, reverse-proxy, serveurs internes et supervision. Tout fonctionne sur un seul hôte Proxmox VE ; Kali Linux joue l'attaquant (depuis « Internet » ou depuis un poste interne compromis) et sert à vérifier que les règles font bien ce qu'on attend d'elles.

Principe pédagogiqueOn ne se contente pas de configurer : chaque règle est prouvée par un test. Un flux autorisé doit fonctionner, un flux interdit doit échouer, et le blocage doit apparaître dans les journaux.
Règle absolue — cadre légalLes outils de Kali Linux ne s'utilisent que sur le laboratoire de la classe, sur les adresses indiquées dans ce cahier. Scanner ou attaquer un système sans autorisation écrite est un délit (accès frauduleux, articles 323-1 et suivants du Code pénal). Ne jamais lancer un scan vers le réseau de l'établissement ou vers Internet. Vérifiez toujours l'adresse cible avant d'appuyer sur Entrée.

Objectifs

  • déployer un laboratoire virtualisé (bridges Linux, VLAN 802.1Q, machines clonées depuis des gabarits) ;
  • installer et configurer deux pare-feu (pfSense ou OPNsense), des zones de confiance et une politique deny all ;
  • publier un service via un reverse-proxy en DMZ (NAT, redirection de ports, TLS) ;
  • segmenter le réseau interne en VLAN et filtrer les flux inter-VLAN selon le moindre privilège ;
  • auditer l'architecture avec nmap et Kali Linux, comparer réseau plat et réseau segmenté ;
  • durcir les serveurs (SSH, pare-feu local, services inutiles), centraliser les journaux ;
  • produire des livrables professionnels : schéma annoté, matrice de flux, fiche de recette, rapport d'audit.

Étape N — Créer le bridge d'installation vmbr9

Sur : PROXMOX — console de pve1

Sur un serveur, les machines préparées au TP0 utilisent vmbr0 pour accéder à Internet. Sur PC, on crée à la place vmbr9 qui partage la connexion de pve1. Partout où le cahier parle du « bridge d'installation », utilisez vmbr9 (PC) ou vmbr0 (serveur).

$ nano /etc/network/interfaces
# ajoutez ce bloc en fin de fichier :
auto vmbr9
iface vmbr9 inet static
    address 10.99.99.1/24
    bridge-ports none
    bridge-stp off
    bridge-fd 0
    post-up   echo 1 > /proc/sys/net/ipv4/ip_forward
    post-up   iptables -t nat -A POSTROUTING -s 10.99.99.0/24 -o vmbr0 -j MASQUERADE
    post-down iptables -t nat -D POSTROUTING -s 10.99.99.0/24 -o vmbr0 -j MASQUERADE
#NAT-INSTALLATION
$ ifreload -a
$ ip -br a show vmbr9
vmbr9 UP 10.99.99.1/24
$ iptables -t nat -L POSTROUTING -n
MASQUERADE all -- 10.99.99.0/24 0.0.0.0/0

Une machine rattachée à vmbr9 reçoit une adresse fixe dans 10.99.99.0/24, passerelle 10.99.99.1, DNS 1.1.1.1. Une fois la préparation terminée, détachez chaque machine de vmbr9 : le laboratoire doit être isolé pendant les tests et les scans.

Cadre légalVous n'attaquez que les adresses 203.0.113.0/24, 172.16.50.0/24 et 192.168.x.0/24 de votre laboratoire. Relisez l'adresse de chaque commande avant de valider.

6.1 Lire un résultat nmap

ÉtatSignificationCe que cela indique

Ajoutez -Pn quand le pare-feu bloque le ping : sans cette option nmap conclut à tort que l'hôte est éteint.

6.2 Test guidé T1 : scan depuis « Internet »

Sur : KALI — carte sur vmbr3 (rôle KALI-EXT)

Avant de lancer, écrivez dans la fiche de recette ce que vous attendez (6.7). Puis :

$ nmap -Pn -p- --min-rate 1000 203.0.113.1
Not shown: 65533 filtered tcp ports (no-response)
80/tcp open http    443/tcp open https

Sur 65 535 ports, seuls 80 et 443 répondent : c'est exactement la surface d'attaque voulue (les deux redirections NAT vers le reverse-proxy).

6.3 Test guidé T5 : scan depuis un poste du VLAN 10

$ nmap -Pn -p 22,80,8080,3306 192.168.20.20 192.168.20.30
192.168.20.20 → 8080 open ; 22, 80, 3306 filtered
192.168.20.30 → tout filtered

Comparez avec le TP1 : ici l'attaquant n'atteint plus que l'application, sur un seul port.

6.4 Test guidé : simuler la compromission du reverse-proxy

Sur : RP-DMZ — vous êtes « dans la peau » de l'attaquant qui a pris RP-DMZ
$ nc -zv -w 3 192.168.20.20 8080
Connection to 192.168.20.20 8080 port succeeded!
$ nc -zv -w 3 192.168.20.30 3306
timed out
$ nc -zv -w 3 192.168.10.100 22
timed out

Même avec RP-DMZ compromis, l'attaquant ne peut atteindre qu'un seul service interne.

6.5 Retrouver les blocages dans les journaux de FW-INT

Status > System Logs > Firewall : chaque tentative refusée est tracée (interface d'arrivée, source, destination, port). Exemple : Block USERS 192.168.10.100:44012 → 192.168.20.20:22 TCP:S ; Block DMZ_LINK 172.16.50.10:39418 → 192.168.20.30:3306 TCP:S.

TP7 — Durcissement et journalisation

Durée 2 h · Objectif ajouter la défense en profondeur côté serveurs (base, SSH, pare-feu local, services inutiles) et centraliser les journaux · Prérequis TP6, accès à la console Proxmox en cas de verrouillage SSH · À rendre captures, journaux centralisés, réponses.

7.1 Moindre privilège sur la base de données

Sur : SRV-BDD — console Proxmox
$ sudo mysql -e "DROP USER 'app'@'%'; CREATE USER 'app'@'192.168.20.20' IDENTIFIED BY 'Un_Mot_De_Passe_Robuste_2026'; GRANT SELECT ON clients.* TO 'app'@'192.168.20.20'; FLUSH PRIVILEGES;"
$ sudo mysql -e "SELECT user, host FROM mysql.user WHERE user='app';"
app | 192.168.20.20

L'utilisateur ne peut plus se connecter que depuis SRV-APP et ne peut plus que lire.

7.2 Pare-feu local avec ufw

Attention au verrouillageAutorisez SSH avant d'activer ufw. En cas d'erreur, la console Proxmox reste utilisable.
$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing
$ sudo ufw allow from 192.168.30.10 to any port 22 proto tcp
$ sudo ufw allow from 192.168.20.20 to any port 3306 proto tcp
$ sudo ufw enable
$ sudo ufw status verbose
22/tcp ALLOW IN 192.168.30.10 · 3306/tcp ALLOW IN 192.168.20.20

7.3 SSH par clés, sans mot de passe

Sur : KALI — poste d'administration : VLAN Tag 30, 192.168.30.10/24
$ ssh-keygen -t ed25519
$ ssh-copy-id etudiant@192.168.20.30
$ ssh etudiant@192.168.20.30
connexion sans mot de passe

Puis sur SRV-BDD, éditez /etc/ssh/sshd_config :

PermitRootLogin no
PasswordAuthentication no
AllowUsers etudiant
MaxAuthTries 3
$ sudo sshd -t && sudo systemctl reload ssh

Toujours tester dans un second terminal avant de fermer la session. Depuis un poste sans la clé, la connexion doit être refusée : Permission denied (publickey).

7.4 Réduire la surface d'attaque web

Sur : SRV-APP — console
$ sudo rm /etc/nginx/sites-enabled/default
$ sudo systemctl reload nginx
$ ss -tlnp
0.0.0.0:8080 (nginx) · 0.0.0.0:22 (sshd)   → le port 80 n'écoute plus
Sur : RP-DMZ — masquer la version et ajouter des en-têtes de sécurité
# dans /etc/nginx/nginx.conf, bloc http { ... } :
server_tokens off;
# dans /etc/nginx/conf.d/proxy.conf, bloc 'listen 443' :
add_header Strict-Transport-Security 'max-age=31536000' always;
add_header X-Content-Type-Options nosniff;
$ sudo nginx -t && sudo systemctl reload nginx
$ curl -k -I https://localhost | head -n 5
Server: nginx · Strict-Transport-Security: max-age=31536000 · X-Content-Type-Options: nosniff

Mettez aussi les serveurs à jour (sudo apt update && sudo apt full-upgrade -y) pendant une courte fenêtre d'accès Internet via le bridge d'installation.

7.5 Centraliser les journaux dans SRV-LOG

Sur : SRV-LOG — recevoir les journaux
$ sudo nano /etc/rsyslog.d/10-recevoir.conf
module(load="imudp")
input(type="imudp" port="514")

$ sudo systemctl restart rsyslog
$ ss -ulnp | grep 514

Sur : SRV-BDD — envoyer ses journaux
$ echo '*.* @@192.168.30.20:514' | sudo tee /etc/rsyslog.d/90-envoi.conf
$ sudo systemctl restart rsyslog
$ logger "test centralisation depuis srv-bdd"

Autorisez ce flux sur FW-INT, interface SERVERS : Pass, TCP, source SRV_BDD, destination SRV_LOG, port 514, Log coché, avant la règle de blocage. Puis faites envoyer les journaux du pare-feu : Status > System Logs > Settings > Enable Remote Logging, serveur 192.168.30.20:514, Firewall Events.

TP8 — Projet final et livrable

Durée 2 h + travail personnel · Objectif rassembler et justifier le travail : produire le dossier d'architecture sécurisée de l'entreprise fictive « Lab SA » · À rendre dossier PDF (schéma annoté, matrice, recette, rapport, justification) + sauvegardes.

ScénarioLab SA compte 60 salariés. Elle publie un portail client, héberge une base de clients et accueille régulièrement des visiteurs. Le DSI vous demande un dossier démontrant que l'architecture protège le portail, la base et le poste d'un salarié, et que les flux sont maîtrisés.

8.1 Réaliser le schéma annoté avec draw.io

  1. Ouvrez app.diagrams.net (ou draw.io Desktop), nouveau diagramme vierge.
  2. Dessinez les zones comme des rectangles de couleur : Internet (gris), DMZ (orange), VLAN Utilisateurs (bleu), Serveurs (vert), Management (violet), Guests (gris clair).
  3. Placez les équipements : FW-EXT, FW-INT, switch virtuel (trunk 802.1Q), RP-DMZ, SRV-APP, SRV-BDD, SRV-LOG, postes.
  4. Tracez les flux par des flèches orientées du côté qui initie la connexion, avec protocole et port (« TCP 443 », « TCP 8080 »).
  5. Ajoutez le plan d'adressage et les numéros de VLAN, une légende des couleurs, et numérotez les flux en renvoyant à la matrice.
  6. Exportez : File > Export as > PDF (ou PNG).

8.3 Rédiger la justification des choix (1 à 2 pages)

  • Contexte et besoins : services à exposer, données sensibles ;
  • Risques identifiés : intrusion externe, propagation latérale, rançongiciel, fuite de données ;
  • Choix d'architecture : pourquoi un double pare-feu, pourquoi ces VLAN, pourquoi tel service en DMZ ; alternatives écartées ;
  • Politique de filtrage : deny all, moindre privilège, ports retenus, journalisation ;
  • Mesures complémentaires : durcissement, SSH par clés, supervision, sauvegardes ; ce qui reste à faire (limites).
