Corrigé

Préparation, résultats attendus et corrections du cahier de TP. Document pensé pour l'enseignant : si vous suivez ce parcours en autonomie, essayez d'abord de répondre seul(e), puis comparez.

ConseilComparer votre travail à la correction n'a de valeur qu'après avoir tenté le test ou la question. Notez d'abord ce que vous attendez, puis vérifiez.

1. Préparation avant la première séance

Check-list de préparation

Organisation conseillée

  • Groupes de 2 étudiants, un laboratoire par groupe. Charge approximative : 6 à 8 vCPU, 12 à 16 Go de RAM (Kali : une seule VM en configuration minimale).
  • Faire valider le TP2 (pare-feu) par l'enseignant avant le TP3 : une erreur de routage entre les deux pare-feu fausse tous les tests suivants.
  • Imposer un snapshot à la fin de chaque TP.
  • Variante OPNsense : mêmes principes, menus différents (Firewall > Rules, Firewall > NAT > Port Forward, alias dans Firewall > Aliases). Désactiver le blocage des réseaux privés sur le WAN.
  • Variante sans pfSense : deux VM Linux routeurs avec nftables, pour les groupes à l'aise en ligne de commande (plus long).

Variante : laboratoire sur le poste de chaque étudiant

  • Vérifier les PC : x86 avec VT-x ou AMD-V activé, 16 Go de RAM, 120 Go libres (Mac Apple exclus) ;
  • Hyperviseur commun à la classe (VMware Workstation ou Hyper-V), conditions de licence confirmées ;
  • Anticiper le conflit Hyper-V / WSL2 / intégrité de la mémoire sous Windows ;
  • Distribuer une VM Proxmox préconfigurée (OVA) avec bridges, gabarits et conteneur WEB-EXT pour gagner le TP0 ;
  • Imposer le profil léger sur les PC de 16 Go ; prévoir un poste de secours ;
  • Compter 30 à 50 % de lenteur : 15 à 20 minutes de plus pour le TP2. Les résultats attendus de la recette sont identiques.

FW-INT / GUESTS1. Pass TCP GUESTS net vers !RFC1918 ports 80, 443. 2. Block any, log.

5. Réponses attendues aux questions

QuestionÉléments de réponse
0.1Un bridge VLAN aware filtre et étiquette les trames 802.1Q ; le VLAN Tag d'une carte la place en port d'accès de ce VLAN. Sans tag, la carte est un trunk qui reçoit tous les VLAN.
0.2Reproductibilité, rapidité, cohérence des versions et du durcissement de base ; moins d'écarts de configuration, correctifs appliqués une fois sur le gabarit.
0.3Les bridges isolés n'ont pas d'accès Internet ; les installations passent donc par vmbr0 (ou vmbr9) en phase de préparation.
1.1Tous les services des serveurs (SSH, base, application, éventuellement port 80). Le SSH et la base n'ont pas de raison d'être joignables depuis un poste utilisateur.
1.2Confidentialité (lecture de la table), Intégrité (écriture possible), Disponibilité (suppression, arrêt du service), Traçabilité (action non journalisée côté base).
1.3Après une première intrusion, l'attaquant explore et rebondit de machine en machine ; en réseau plat rien ne l'arrête.
1.4Segmentation en VLAN, filtrage inter-zones, moindre privilège, pare-feu local sur les serveurs, DMZ pour l'exposé.
2.1Politique deny all et moindre privilège : on autorise explicitement ce qui est nécessaire, rien d'autre.
2.2Entre DMZ et LAN, on route pour conserver les adresses réelles dans les journaux et les règles ; le NAT sortant est fait par FW-EXT, à la frontière avec Internet.
2.3Elle évite de se couper l'accès à l'interface d'administration par une règle trop stricte ; ne pas la retirer sans solution de secours (console).
3.1Aucune règle n'autorise ces flux : deny all. Le DHCP fonctionne car pfSense crée automatiquement les règles nécessaires au service DHCP activé sur l'interface.
3.2Une ligne de blocage identifie interface, IP source, IP destination, port et action (Block), par la règle « Default deny ».
3.3Non : le trafic inter-VLAN passe par le routeur (FW-INT) ; c'est ce qui permet de le filtrer.
3.4Non : le VLAN sépare, c'est le filtrage entre VLAN qui protège.
4.1Les trois premiers passent par le NAT et RP-DMZ ; le réseau interne n'est ni routé ni autorisé depuis le WAN. Deux barrières successives (FW-EXT puis FW-INT).
4.2172.16.50.10 (RP-DMZ), car le proxy ouvre sa propre connexion ; X-Forwarded-For / X-Real-IP conservent l'adresse du client.
4.3Un seul flux : 192.168.20.20:8080. Pour réduire : WAF, durcissement et isolement du reverse-proxy, IDS, supervision, règle limitée aux méthodes et chemins nécessaires.
4.4Les utilisateurs qui tapent http:// sont redirigés vers HTTPS au lieu de recevoir une erreur ; on ne sert aucun contenu en clair.
5.1Il n'a aucun besoin légitime de la base ; si un accès est requis, il passe par une couche applicative interne. Principe de moindre privilège.
5.2Cela faciliterait l'exploitation de tout service vulnérable, l'attaque par force brute sur SSH ou la base, et la propagation latérale.
5.3Block abandonne sans réponse (le scanneur voit « filtered » et ralentit) ; Reject renvoie un refus et révèle l'existence de l'hôte. Block est préférable côté Internet.
5.4La première règle qui correspond s'applique ; placer un « block any » avant un « pass » rend le pass inopérant.
6.1Lignes de blocage identifiant interface, IP source, IP destination, port et règle (« Default deny » ou règle de blocage explicite).
6.2Réseau plat : tous les ports de service atteignables ; réseau segmenté : un seul port (8080) atteignable.
7.1Deux fois : réseau (FW-INT) et hôte (ufw, côté base). Défense en profondeur.
7.2Limite les dégâts si l'application ou le compte est compromis : pas d'écriture, pas d'usage depuis un autre poste.
7.3L'événement est visible côté pare-feu et serveur ; les journaux restent disponibles même si le serveur est compromis ou effacé.

6. Erreurs fréquentes et pistes d'aide

Erreur observéePiste pour l'étudiant
Passer un VLAN Tag sur la carte du pare-feu interne côté trunkRappeler que la carte de FW-INT doit rester sans tag pour recevoir tous les VLAN.
Oublier la route de RP-DMZ vers 192.168.0.0/16 via FW-INTFaire tracer le chemin avec traceroute et regarder les journaux des deux pare-feu : le routage asymétrique en est la cause.
Réponses du trafic entrant par DMZ_LINK qui repartent via FW-EXTSur FW-INT, cocher « Disable reply-to on WAN rules » dans System > Advanced > Firewall & NAT.
Laisser « Block private networks » sur le WANLe trafic de KALI-EXT (adresses de laboratoire) est rejeté ; décocher les deux blocages sur les WAN de laboratoire.
Écrire les règles avant la matrice de fluxRefaire dans l'ordre : décider, écrire, tester, prouver.
Règle « pass any any » ajoutée « pour tester »Exiger sa suppression ; une règle temporaire doit porter un commentaire et une date.
Verrouillage SSH après ufw ou sshd_configConsole Proxmox ; toujours tester dans un second terminal avant de fermer la session.
Résultats de nmap mal interprétés (filtered et closed confondus)Reprendre le tableau d'interprétation du TP6.

7. Barème indicatif et attendus de niveau

NiveauDescription
MaîtriseArchitecture complète fonctionnelle, matrice et règles cohérentes, tests prouvés par journaux, justification argumentée (alternatives, limites).
SatisfaisantZones et VLAN en place, DMZ fonctionnelle, matrice correcte, quelques tests non prouvés ou règles trop larges.
FragileSegmentation partielle, règles permissives, tests non rattachés à la matrice, justification descriptive.
InsuffisantPare-feu non opérationnel, DMZ sans filtrage, absence de preuves.
